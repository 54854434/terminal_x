## 7. 玩法与内容评审：下一阶段的产品原则（v3.7 新增）

**来源与边界**：以下“现状”通过交接文档及 GitHub `lib/engine/tx_session.dart`、`lib/main_terminal_v02.dart` 等源码核对；“建议”尚未实现，不可写成已有功能。Terminal X 的定位继续是**离线、单人、专业交易与大资金操盘模拟器**，不改造成社交、剧情或充值升级游戏。

### 7.1 已证实的游戏循环与短板

- 初始账户 `100000000` 分，即 **¥1,000,000** 模拟现金；两只标的 `SIM-A01` 初始参考价格 ¥10.00，`SIM-A02` 初始 ¥25.00。做市商分别初始持有 25,000 股和 2,500 股；资金、库存有限，不能凭空补单。
- 现有循环：查看模拟 K 线与五档盘口 → 选择市价/限价、股数/价格 → 撮合/冻结/撤单 → 行情单步或自动步进 → 查看资产与最近 100 条委托/成交。只有四个一级页面，主要侧重功能操作。
- `TxSession.nextTick` 的参考价增量由 `((step * 17 + i * 11 + 3) % 7) - 3` 确定，**7 步周期重现且净变动为零**（在没有成交价覆盖时）。因此当前不具备持续的行情趋势/波动状态或不可预知的市场环境。不要把 deterministic quote drift 描述成真实随机市场。
- 市场不具备独立策略性对手交易流；主要依赖预置的有限做市商盘口与玩家成交。K 线成交量只来自记录的真实撮合，不能为了视觉活跃而虚构成交。
- `totalAssetsCents` 依照 `lastPrice` 标记持仓，`lastPrice` 可能受玩家最新成交价格影响；**当前总资产估值不代表可按实际五档全部平仓的净值**。缺少成交均价、已实现/浮动盈亏、最大回撤、交易成本与可清算市值，用户很难判断操作效果。
- 每次交易与步进保存完整快照，历史快照重复包含增长中的订单、成交和账本；长期模拟对空间、加载和计算的压力仍未测试。当前自动步进单轮上限 60 步是保护措施，不应视为长期无限模拟已达成。

### 7.2 面向“专业操盘”的建议玩法闭环

以 **“观察市场 → 制定仓位与委托计划 → 预估成交/风险 → 执行和追踪 → 复盘收益/滑点/回撤 → 根据新的市场状态重新决策”** 为核心。自由沙盘为默认模式；情景挑战是可选内容，避免强制关卡、剧情和签到。

| 优先级 | 建议模块 | 给玩家的价值 | 实现底线 |
|---|---|---|---|
| P0 | 成交前预估和确认 | 直观看见扫过几档、预计加权成交价、可能滑点、未成交余量、资金/持仓占用 | 使用真实盘口只读计算，不直接改写订单簿；提交时重新按最新盘口撮合 |
| P0 | 组合收益与风险面板 | 已实现/浮动盈亏、收益率、峰值回撤、成本、卖出可清算估值、买卖点原因 | 整数分成本核算、明确估值依据；不得将最近成交价误标为保证可实现净值 |
| P0 | 情景化市场状态 | 趋势、震荡、波动放大、流动性抽离，各种状态切换让交易有真实决策空间 | 固定种子可复现、状态完整落库、订单和资金守恒、没有虚构成交与无限做市资金 |
| P1 | 专业委托管理与风控 | 订单筛选、撤单确认、单笔风险、限价与滑点保护、最大仓位控制 | 提前拒绝不合法单，不能打破已有撮合/冻结/事务边界 |
| P1 | 可选择的操作挑战 | 例：用给定现金在期限内完成大额建仓，同时控制冲击成本、最大回撤与剩余现金 | 可跳过、不改自由沙盘；评分公式公开，条件可复现，模拟市场而非实盘建议 |
| P2 | 更丰富的资产和制度 | 逐步添加模拟市场、不同流动性、费用和结算规则 | 先建立可用性和真实性，再扩展资产数量；费用须真实落账且有对手账户 |
| P2 | TWAP/VWAP、策略、分支存档 | 大资金分批执行、复盘多个方案 | 先完成市场演化、风险反馈和存储可扩展性再引入；不可在空洞静止盘口下伪称专业算法效果 |

### 7.3 建议的版本拆分与自动验收

**V0.3 首批（V0.2.1 稳定性修复确认后）**：先交付“操作与收益解释层”，包括交易预估/限价滑点警示、持仓成本和已实现/未实现盈亏、撤单与拒单的可解释反馈、组合资金和盘口风险概览。保留现有模拟市场算法但对用户标注为有限测试环境。本批必需添加单元测试涵盖多个盘口价格档、零流动性、部分成交、冻结与撤单、盈亏符号/成本基准及无仓位场景；交易行为与 SQLite 仍按已验证不变量回归。

**V0.4 第二批**：基于存档种子的可复现市场状态机、模拟行情事件与多类有真实资金库存的交易参与者；设计有明确交易后果的趋势/震荡/波动/流动性情景，并引入独立订单流。需要测试同种子重放、两标的差异、资金与库存守恒、断点恢复、异常存档拒绝，以及行情步进不凭空成交。

**V0.5 体验内容批次**：自由沙盘保持默认；增加**可选**策略/执行情景，记录目标、起始资金、期限、成交均价/滑点、收益与回撤，允许阶段复盘；没有证据时不宣称“真实世界投资结果”。随后才考虑做市制度、衍生品与杠杆。

### 7.4 紧随 V0.2 之后要检查的产品风险

1. **价格参考 / 市值标记 / 可清算市值**分开显示，避免自成交或跨档最新成交诱导虚假收益感。
2. 余额和持仓守恒必须维持；玩家选择的自由挑战不能额外生成现金或持仓。持久化失败必须保留现场并停止交易。
3. 行情驱动必须有已落库种子和事件史，避免一次关闭 App 之后重放路径发生变化。
4. 新内容不得要求重做 V0.1b/V0.1c 已完成的手机测试；每批 CI 继续自动回归，手机只在重要里程碑集中验收。
5. 针对完整快照数据增长安排压力测试及归档/结构化记录，防止丰富行情后快速占满手机空间。

## 8. V0.2 实机反馈与 V0.2.1 批量修复（2026-10-12）

### 8.1 已知已通过与未通过

用户手机 V0.2 完成**6/6 基础项目**：行情/交易/资产/记录四页、SIM-A01/A02 五档及 K 线操作、市价买卖联动、限价冻结撤单、1×/5×/10×与单步操作、彻底关闭重新打开后现金/持仓/委托/步数恢复。后续不要求重复这六个项目的旧版本验收。

**另有三项 V0.2 当前未通过**：K 线几乎不动；模拟步缺少按 24 小时制计算的游戏时间；倍速或步数变大后卡顿、停不住地跳步。这些问题有明确代码原因：
- `TxSession.nextTick()` 的旧参考价在 7 步内净增量为零，趋势不可持续。
- 旧 UI 仅显示整数 `step`，使用周期性 `Timer`；不包含 24 小时游戏时间语义。
- 旧 UI 每次 SQLite 交易成功后重复读取和解码最近 **160 个完整历史快照**，而每个快照包含不断增长的订单、成交和完整账本；自动定时器可能在设备卡顿后让用户感到控制不清晰。

### 8.2 V0.2.1 修复包（本次已生成，CI 与实机尚未验证）

- **新的、与已有 V0.2 并存的 APP**：`com.terminalx.v021.terminal_x`，入口 `lib/main_terminal_v021.dart`；不访问 V0.2 或任何 V0.1 旧包的数据。不要卸载旧 APK 或清空数据。选择新包名是因为 GitHub debug APK 签名未建立可靠的升级链。
- **游戏时钟**：模拟第 1 天 **09:30** 开始，成功提交 1 步 = 游戏内 **1 分钟**。第 870 步为第 2 天 00:00；满 1440 分钟转回次日 09:30。24 小时连续沙盘制，不是已实现股票交易时段制度（后续规划）。
- **速度映射**：1× = 每现实 5 秒前进 1 个游戏分钟；5× = 每 1 秒；10× = 每 0.5 秒。受 SQLite 提交速度影响，如果数据库慢会**自动降实际推进频率**，但绝不追补落后的分钟、跳过序号或放大积压队列。每次自动运行最多 60 游戏分钟后自动暂停，防止数据骤增；App 退到后台也暂停。
- **行情**：新的确定性、不含外部数据的行情增量随 120 游戏分钟阶段轮换，上行/横盘/下行/高波动，保证不像原来的 7 步循环；每次修改真实参考价再重挂有限库存做市报价，**不创造假成交量**。更高级的种子市场与异质订单流仍属未来 V0.4，当前只是 V0.2.1 稳定性修复。
- **K 线与性能**：在 SQLite open 时读取最近 64 个已校验快照形成内存 K 线缓存，此后每个成功提交的交易/步进，仅从“提交前与提交后”两个状态增量更新 K 线，避免每步查询和反序列化 160 份完整历史快照。数据库本身仍保留完整审计快照；本批次不删除/压缩任何真实存档。
- **新增自动化测试**：`test/tx_v021_market_test.dart` 校验时钟跨日、速度间隔、价格变化、同样步骤的确定性及断点恢复；`test/tx_live_candles_test.dart` 校验真实成交量/时序、不重复历史全量解码、重建一致性与失序拒绝。保留所有现有回归测试及 Android APK 编译测试。
- **注意测试/发行状态**：本包 ZIP 只是源码层的交付稿，**尚未在 Actions 验证是否编译或能稳定运行**。后续依据 V0.2.1 工作流准确日志修复任何新出现问题；CI 绿色之后才要求一次简短手机定向回归，不能预先承诺已解决实测卡顿。
- **仍存在的长期性能风险**：每步保存完整快照且订单/账本仍增长，长时间无人值守运行的空间性能尚未解决；V0.3/V0.4 应安排结构化增量账本、历史归档及千步压力测试，禁止为了提速删历史或破坏账务守恒。
